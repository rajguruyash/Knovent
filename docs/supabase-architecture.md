## The tables

All business-owned tables carry `business_id`, and every child row points at its parent with `(id, business_id)`, so a row can never belong to a different business than its parent (tested: the database refuses it even for the server).

| Area | Tables |
|---|---|
| Tenancy | `profiles`, `businesses`, `business_members` (roles `owner`, `admin`, `editor`, `viewer`), `business_settings` |
| Knowledge | `knowledge_sources`, `knowledge_source_versions`, `faqs`, `document_chunks`, `embeddings` (`extensions.vector(384)`, HNSW cosine index), `learned_questions` |
| Conversations | `conversations`, `messages` (outcome, evidence, retrieval, model use), `feedback` |
| Evaluation and release | `evaluation_datasets` (roles `development`, `regression`, `locked`), `evaluation_questions`, `evaluation_results`, `knowledge_versions` |

| AI inference consent | `ai_inference_consents` (migration 10) |

The proposed list in the task (`profiles`, `businesses`, `business_members`, `business_settings`, `knowledge_sources`, `faqs`, `document_chunks`, `embeddings`, `conversations`, `messages`, `feedback`, `evaluation_datasets`, `evaluation_results`, `llm_provider_configs`, `usage_records`, `audit_logs`) is all present; the repository had no earlier Supabase schema, so nothing was duplicated. ## Row level security

* **Reading:** a person reads a row only if they belong to its business (`is_member`). The helpers are `SECURITY DEFINER` with an empty `search_path`, so they cannot be shadowed and do not depend on the policies they serve.
* **Writing:** editors and above write sources, FAQs and learned questions; admins and owners manage people, settings, the model and datasets; **only the server** writes chunks, embeddings, conversations, messages, usage and audit rows (client roles have no INSERT/UPDATE/DELETE privilege on them).
* **No direct business insert.** `create_business(name, slug)` makes the caller the owner. A client cannot choose someone else as owner (tested).
* **Owners:** only an owner can make or change an owner, and a business always keeps at least one.
* **Columns the server owns** (`businesses.owner_id`, `slug`, `deleted_at`; a source's `version`/`checksum`/counts; the model configuration's `has_key`/`key_status`) cannot be updated by a client, by column-level grants.
* **The key:** `llm_provider_secrets` has RLS enabled and **no policy**, and `authenticated`/`anon` have no privilege on it. Only the server reaches it. The ciphertext is AES-256-GCM, bound to the business id; the encryption key is in the service's environment, not the database.
* **Locked evaluation questions** are visible to owners and admins only.
* **Storage:** files live at `<business id>/<source id>/<file>`. The policies read the first path segment: members read, editors and above upload, admins delete; a path whose first segment is not a business id is refused by every policy; a source's `storage_path` must start with its own business id (a table CHECK).
* **The server connection bypasses RLS** (it acts for many businesses), so every query in `src/faqengine/hosted/store.py` is bound to a business id and every request first has its role re-checked in the database. `tests/test_hosted.py` proves two businesses in one service cannot see each other.
* Inside a `SECURITY DEFINER` function the session user is always the function's owner, so such functions authorise with `has_role(...)` or the JWT's role claim (`auth.role() = 'service_role'`), never with `is_server()`. (A test caught exactly this mistake in an earlier draft of `delete_business_data`.)

## Where retrieval happens: pgvector and the in-memory index

Embeddings are stored in `embeddings.embedding` (`vector(384)`, one row per way of asking, per question-with-answer, per chunk), with an HNSW cosine index and a plain btree on `business_id`.

The hosted service does **not** run its hybrid ranking in SQL. It loads one business's active rows and vectors into memory (rebuilt when `index_token` changes) and runs the same `runtime/retrieval.py` as the local engine, so the keyword channel, the blend, duplicate handling and the guard are one implementation, not two. Duplicating them in SQL would give two sets of business rules.

`match_embeddings(business, query_vector, k)` (SECURITY INVOKER, so RLS applies) is provided for tenants too large for memory or for ad-hoc inspection; **nothing in the service calls it yet.** For the usual business (hundreds to a few thousand entries) a full in-memory scan is exact and takes well under a millisecond per question after load.

## Updating a source

`replace_content` (in the service's store) runs in **one transaction**: deactivate everything of the older version (`supersede_source_content`), insert the new FAQs, chunks and vectors (skipping text already active elsewhere in the business: a unique partial index also forbids duplicates), record a `knowledge_source_versions` row with what was added, removed and unchanged, and mark the source ready. If anything fails the transaction rolls back and the last good reading stays searched (tested). Unchanged files (same checksum) are not reprocessed.

## AI inference consent (migration 10)

| Rule | Where it is enforced | Tested by |
|---|---|---|
| Only an owner or admin of the business can grant or revoke; editors, viewers, non-members and another business's owner cannot | RLS policies `ai_consent_grant`, `ai_consent_revoke` + column grant (only `status`) | `tests/test_ai_consent.py` |
| The person recorded as granting is the person acting, whatever the request says | `ai_consent_guard` trigger (`granted_by := auth.uid()` unless the server names who) | same |
| A grant can only become revoked: no edit, no un-revoke, no delete (the history is the audit); a new agreement is a new row; one active grant per business and provider | guard trigger + partial unique index | same |
| Consent is per provider and per disclosure version | `ai_consent_allows(business, provider, version)` | same, `tests/test_hosted_pipeline.py` |
| Another business cannot read or change it | RLS (`is_member`) | same |
| No credentials in it | no such column; provider keys stay in `llm_provider_secrets` | same (schema check) |
| Every grant and revocation is in the audit trail with who, which provider and version; never content | `audit_event()` branch for the table | same |
| The service asks before every external call and a revocation blocks the next one | `hosted/service.py: DbConsent` → `Store.consent_allows` (no cache; any error means no) | `tests/test_hosted_pipeline.py` |

## Freshness, and one view over every kind of source (migration 09)

All sources, whatever they are (FAQ table, document, spreadsheet, JSON, web page), end up as `faqs` or `document_chunks` with vectors and are searched in one ranking; the database never needs to know the kind of a customer's question. What it records about each source, besides name, type, address or storage path, version, checksum and counts:

* `valid_from`, `valid_until` (dates) and `supersedes` (the names of the sources it replaces). A file can state them itself in a front-matter header (`valid_until: 2026-12-31`, `effective: …`, `supersedes: old.md`), which the service stores on ingest; a person with the editor role can also set them in the app. A date that is not a date, or an end before the start, is dropped **with a warning** and never stops the text from being read. When the file states nothing, what a person set stays.
* The service computes, **per day**, which entries are not current (the same `runtime/validity.py` as the local engine; the day is part of the cached index's token, so a source expires at midnight without anyone touching it) and leaves them out of retrieval. A replacing source only counts once it is itself ready and in force.
* `public.knowledge_units` answers "what does this business know, and from where" for the person who owns it: `unit_kind` (faq / passage), `source_name`, `source_type`, `source_location` (address or storage path), `heading`, `content`, `version`, `ingested_at`, `valid_from`, `valid_until`, `supersedes`, `source_status`, `superseded_by`, `is_current` (by dates and replacement). Tested as three different people and as `anon`.

Lifecycle, as tested on the real schema with the real embedding model (`tests/test_unified_hosted.py`): reading a source again with the same bytes does nothing; with changes it supersedes the old reading in one transaction (no duplicates, the old reading is kept inactive as history, what changed is recorded); deleting a source removes its FAQs, passages and vectors and the answers that came from them; a source that cannot be read leaves the others, and its own last good reading, alone; a web page keeps its own address as the source its passages are cited from.

## Evaluation integrity in the database

Enforced by triggers and constraints, tested:

* a question cannot appear twice in a set, in two sets, or as an FAQ question, an alternative phrasing or a learned question (compared after lower-casing and removing punctuation);
* questions of one group (paraphrases of one fact) cannot be split across sets;
* the reverse: an evaluation question can never be added to the knowledge or learned from feedback;
* a locked set can be sealed once; sealed sets accept no new, changed or deleted questions; its results are append-only and may only be `final_report`; a release gate may only be measured on the regression set;
* `knowledge_versions`: a version goes active only with a passed `promotion_gate` result behind it, only one version is active, and `rollback_to_version` returns to a version that was live before.

Near-duplicates (paraphrases that share few words) cannot be detected by a SQL equality test; that check stays in the Python evaluation code (`docs/dataset-integrity.md`).

## Audit trail and deletion

`audit_logs` is append-only (even the database owner cannot edit or delete a row). It records member changes, model configuration changes (provider, model, on/off; **never a key**), source deletions, sealing of datasets and version changes. `delete_business_data(business)` (owner only) removes everything the business owned in one statement (foreign keys cascade, including the key, the audit rows and the members) and leaves a `deletion_receipts` row with counts and no content.

## Not built

* Inviting a person by e-mail address (needs the service role and an e-mail flow); members are rows in `business_members`.
* A scheduled retention job for `messages` (the setting `privacy.retention_days` exists; nothing deletes by it yet).
* Edge Functions: none are used. The engine needs a long-lived process and the Python code; the web API is Vercel functions. Adding Edge Functions would add a third place for logic.
